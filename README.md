# sb-user-manager

一个直接运行、按菜单操作的 sing-box 用户管理脚本。无需记命令，可完成安装、添加用户、流量限制、分流和跨服务器迁移。

项目当前状态、路线图和待办分别记录在 [`PROJECT.md`](PROJECT.md)、[`ROADMAP.md`](ROADMAP.md) 和 [`TODO.md`](TODO.md)。产品方向、架构、开发、部署和发布规则分别记录在 [`docs/PRODUCT.md`](docs/PRODUCT.md)、[`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md)、[`docs/DEVELOPMENT.md`](docs/DEVELOPMENT.md)、[`docs/DEPLOYMENT.md`](docs/DEPLOYMENT.md) 和 [`docs/RELEASE.md`](docs/RELEASE.md)。项目采用 [MIT License](LICENSE)；安全问题请按 [`SECURITY.md`](SECURITY.md) 私下报告。

正式发布提供单一脚本 `sb-user-manager.sh`。脚本通过公开 GitHub Release 匿名检查并更新管理脚本、sing-box 和 Nfuse，不要求、读取或保存 GitHub Token。

主界面会在版本号旁显示“公开版”；该标识不会写入故障诊断报告。

## 主要功能

- 菜单式安装、环境修复和版本更新
- 自动识别全新服务器、已有安装或损坏环境，并在修改前创建完整备份
- 原生 SS2022 与 AnyTLS 用户管理；迁移期可让同一用户同时保留一个旧版 SS2022 + ShadowTLS 入口
- 为每个用户设置协议、端口和加密方式；AnyTLS 与旧版 ShadowTLS 用户还可设置连接域名（SNI）
- 设置默认连接域名，并一键同步已有用户
- 编辑用户端口、连接域名、加密方式、每月流量重置日和有效期
- 统计所有用户流量；计费用户可限制每月用量、延长或提前有效期，以及临时或永久调整流量
- 用户到期自动停用
- 用户配置导出
- 按远程规则集把指定流量转发到另一台服务器
- 分流出口支持 AnyTLS、Shadowsocks、SS2022 + ShadowTLS
- 查看、编辑、排序、停用或启用分流，保存前自动检查规则集是否可用
- 操作失败、SSH 断开或服务器重启后自动还原未完成的修改
- 多个 SSH 会话同时操作时，用户、分流、部署、接管、卸载和更新共用单写者锁；已有操作未结束时新操作会明确提示并停止
- 一键检查并修复用户、分流、连接配置和流量统计
- 一键生成自动隐藏敏感内容的故障诊断报告，方便交给维护者排查
- 通过 GitHub Release 检测并更新管理脚本
- 查看 sing-box 最新正式版和测试版，并在切换前验证当前配置及分流规则集是否兼容
- 创建带密码的单文件迁移备份，在新服务器上合并恢复或完全恢复
- 查看每次恢复的结果，并清理过期备份和记录

## 在线更新

“检测更新”会通过 HTTPS 查询公开 GitHub Release，并在安装前验证 GitHub 提供的 SHA-256 digest、脚本语法和版本号。配置文件 `/etc/sb-user-manager.conf` 必须是 `root:root`、权限为 `600` 的普通文件，不能使用符号链接。脚本只读取已知的 `配置项=值`，遇到未知、重复或命令式内容会停止读取，不会把配置作为 shell 脚本执行。

旧私有版配置中的 `GITHUB_TOKEN` 字段只为升级兼容而接受，其内容会被丢弃，不会载入进程、发送到网络或写入新配置。确认已经切换到公开版后可以手工删除该行。

### 从旧私有版永久无损接管到公开版

仍在运行旧私有版时，先从公开仓库的不可变 Release 下载目标 `sb-user-manager.sh`，并按该 Release 公布的 SHA-256 独立校验。然后以 root 直接运行目标脚本的受控接管命令：

```bash
chmod 700 sb-user-manager.sh
./sb-user-manager.sh --take-over-installed-manager
```

接管由新脚本主动完成，因此服务器上的旧私有版不需要预先具备接管功能。目标版本可以与当前版本相同，也可以更高，但绝不允许降级；目标支持的数据版本范围也必须覆盖当前脚本。接管只原子替换 `/usr/local/sbin/sb-user-manager` 和管理脚本版本记录，不修改用户、流量、有效期、证书、分流、sing-box 或 Nfuse，也不会启停任何服务。

原管理脚本和版本记录会保存在 `/var/lib/sb-user-manager/manager-handoff/`。替换、版本记录或最终核验任一步失败都会立即原子恢复；若服务器在接管中途断电，下次运行新脚本时会先完成恢复再进入其他功能。项目不再发布私有版；接管成功后，后续更新全部使用公开仓库。

## 使用方式

以 root 身份直接运行，不需要附加命令：

```bash
chmod 700 sb-user-manager.sh
./sb-user-manager.sh
```

菜单或填写页面中如果输入了文字、无效编号或不符合要求的内容，脚本会说明原因并停留在当前位置等待重新输入，不会因此退出。显示 `0` 的页面可以随时返回上一级；直接关闭 SSH 或结束输入时，当前交互会安全结束。

如果另一条 SSH 会话正在修改用户、分流或系统环境，当前会话会提示“另一个管理操作正在进行”并停止本次操作。请等待前一项操作结束后重试，不要同时运行两个写操作；脚本也会双向检查用户事务与环境事务的恢复记录，避免两套回滚互相覆盖。

不要通过这台服务器自己的代理节点连接它的 SSH 后再执行用户、分流或版本修改；这些操作需要重启 sing-box，代理隧道会随之中断。脚本会核对当前 SSH 套接字是否确实由本机 sing-box 建立，确认命中时会在修改数据前停止，并提示先在 SSH 软件或本地代理中把该服务器地址设为直连。普通 SSH 直连不会受到影响。

第一次使用时进入“系统管理 → 部署与卸载 → 安装或修复环境”。安装完成后，输入简短命令 `sbm` 即可进入管理界面，也可以继续使用完整命令 `sb-user-manager`。`sbm` 由脚本自动维护并固定指向 `/usr/local/sbin/sb-user-manager`；如果服务器上已经有其他同名文件或链接，安装会停止并提示，不会擅自覆盖。以后仍可直接运行最初下载的副本；如果系统中已经安装了更新版本，脚本会自动切换到新版。

在“用户管理 → 编辑用户”中，脚本会先列出用户，再逐项询问。直接回车表示保持原值，端口处输入 `r` 会在 `20001–30000` 中随机选择。修改 SS2022 加密方式会重新生成连接密码，用户需要重新导入配置；修改其他内容不会更换密码。停用中的用户编辑后仍保持停用。

全新部署会在 `/etc/sb-user-manager.conf` 自动写入以下全局默认值，安装过程不会询问：

```bash
SS2022_SHADOWTLS_SNI="publicassets.cdn-apple.com"
ANYTLS_SNI="weKbP9SVYU.download.windowsupdate.com"
```

新建 SS2022 用户不再使用 ShadowTLS，因此无需填写 SNI。添加 AnyTLS 用户时可以填写自己的连接域名，直接回车则使用默认值。`SS2022_SHADOWTLS_SNI` 仅用于兼容升级前已经存在的 SS2022 + ShadowTLS 用户；进入“默认连接域名（SNI）”仍可查看或更换旧版默认值并同步旧版用户。修改旧版 ShadowTLS 域名时连接服务会短暂重启；修改域名不会更换用户密码。

原生 SS2022 使用一个 sing-box 入站在同一数字端口承载 TCP 和 UDP，导出的 Surge 配置会自动包含 `udp-relay=true`，不需要另外填写 UDP 端口。Shadowrocket 导出会显示可直接导入的 URL 和相同内容的二维码。升级前已经存在的 SS2022 + ShadowTLS 用户不会被自动转换，其密码、端口、连接方式、分流和启停状态保持不变，也仍可继续导出和管理。

在“用户管理 → 管理用户协议”中，旧版用户可以在保留原连接的同时添加一个原生 SS2022，并可再添加一个 AnyTLS；三类入口共享同一用户的流量、有效期、启停状态与用户分流。每类入口最多一个，删除或编辑时会明确区分“原生 SS2022”和“SS2022 + ShadowTLS（旧版）”。脚本不会为新用户创建 ShadowTLS，也不会为已有用户新增第二个同类入口。

添加用户时，直接回车默认创建“流量计费用户”，可以设置每月流量和有效期；输入 `2` 创建不限流量、有效期不限但仍统计累计用量的“自用用户”；输入 `0` 返回。既有自用用户升级后会在端口没有冲突时自动接入流量统计；如发现同名记录或端口冲突，脚本不会覆盖原数据，会提示运行“服务与配置检查”。

在“用户管理 → 调整用户有效期”中，输入正整数会按月延长，输入负整数会按月提前。提前前会显示新旧到期时间并要求确认；调整后的时间必须仍在未来，如需立即停止用户应使用“停用用户”。提前有效期不会改变用户启停状态、清零已用流量或重写 sing-box 配置；正数延长保留既有续期与自动启用行为。

停用再启用计费用户时，会清零当前计费周期的已用配额；自用用户停用、启用或更换端口时会保留累计用量。自用用户不会因为用量增加而被阻断，也不参与到期停用、有效期调整或流量配额调整。

导出用户配置时会自动识别服务器公网 IPv4。服务器使用 NAT 时，脚本会通过 HTTPS 查询实际公网地址，并拒绝把 `10.x`、`172.16-31.x`、`192.168.x` 等内网地址写入配置。如果服务器的入口公网地址与出口地址不同，可在 `/etc/sb-user-manager.conf` 中设置 `PUBLIC_SERVER_OVERRIDE="实际公网IPv4"`。二维码由服务器本地组件生成，节点信息不会发送给第三方网站；旧服务器缺少组件时，首次导出会询问是否安装，即使取消也仍会显示完整 URL。二维码保持标准终端 UTF-8 格式，不依赖特定 SSH 客户端的图片显示能力。

“分流管理”列表按使用顺序显示，数字越小越先匹配。增加分流前，先分别进入“预置出口管理”和“预置规则管理”，保存常用出口节点与远程规则集；保存预置本身不会修改 sing-box，也不会影响现有连接。增加分流时只需填写分流名称并选择预置规则、适用用户和预置出口，不再重复填写服务器、密码、规则地址或内部出口名称。

脚本部署后的分流由脚本统一管理。如果 sing-box 中残留了不在用户数据文件内、但远程规则集地址与当前分流相同的旧规则，脚本会把它视为旧版残留，在操作前备份后统一整理，避免旧规则因排序靠前而抢先命中。与当前分流规则地址无关的基础配置不会因此被删除；旧出口仍被其他配置引用时也会保留。

新建分流会与所选预置保持关联。以后修改预置时，脚本会先显示关联分流总数和其中启用数量；启用中的关联分流会一起检查并通过一次服务重启生效，停用分流只更新保存内容并保持停用。删除预置不会删除分流或中断连接，而是让关联分流保留最后一次可用内容并转为“独立配置”。升级前已经存在的分流也会保持独立配置，不会被脚本擅自归入某个预置。

多个用户使用相同预置规则和预置出口时，sing-box 只加载一份规则集和一份出口，用户范围会自动合并；停用其中一条分流不会影响其他用户。同一用户重复选择相同规则和出口会提示无需重复，同一用户不能让同一条规则同时使用两个不同出口，“全部用户”与指定用户发生重叠时也会被拒绝，避免出现难以判断的优先级。

可以继续查看分流详情、修改适用用户或所选预置、改变顺序、停用和启用。分流列表和详情会标明使用的预置名称；内部运行标签和出口密码不会显示。

“验证分流是否生效”会引导选择分流和测试用户。开始记录后，在客户端访问需要验证的网站或应用，再回到脚本按回车；脚本会把这段时间的新连接整理成易读表格，注明命中当前分流、走直连或命中其他分流。诊断过程不会修改配置或重启服务。

新增或编辑分流时，脚本会先下载并检查远程规则集。只有地址可访问、格式正确且当前 sing-box 能识别时才会保存；保存或重启失败会自动恢复修改前的配置。

### mihomo 部署上的分流规则来源

装了 mihomo 的服务器上，添加分流或预置规则时会多问一句「规则从哪里来」，有三种选择：

- **网址**：填一个 HTTPS 的 `.yaml` 规则集地址。保存时脚本会自己下载一次、检查内容确实是规则集且写法与所选写法对得上，通过才保存；下载到本机的文件沿用网址里的文件名，放在 `/etc/mihomo/rules/` 下，之后由 mihomo 每天自动更新一次。
- **本机文件**：自己把规则文件放进 `/etc/mihomo/rules/`，脚本只读不改。
- **GeoSite／GeoIP 类别**：直接填 `GEOSITE,openai`、`GEOIP,us` 这样的类别名，不需要任何规则文件。一条分流可以填多个类别，命中其中任意一个就走这条分流。类别名在保存时由 mihomo 当场校验，写错会立刻告诉你是哪一个不认识。

「分流管理 → 立即更新规则集」用于「现在就要用上新规则」：脚本会把所有网址来源的规则集重新下载并检查一遍。取不到的那几条会保留现在的内容，不会变成空规则；确实有内容变化时会重启 mihomo 让新规则立刻生效，连接会中断几秒，内容没有变化就不重启。平时不点它也没关系，mihomo 每天会自己更新一次。

用到 GeoSite／GeoIP 类别的服务器，会在第一次保存这类分流时自动下载数据库（GeoSite 约 4 MB，用到 GeoIP 再加约 17 MB），放在 `/var/lib/mihomo` 下，之后每 24 小时自己检查更新。没有这类分流的服务器不会下载它们。下载地址可以在「系统管理 → geo 数据源」里查看和修改，留空表示用 mihomo 自带的源；改成取不到的地址时会当场拒绝，原来的设置不变。

同一目录下还可能出现一个 `ASN.mmdb`，那是 mihomo 自己下载与维护的：只要配置里有规则集分流它就会存在，与上面这个设置无关。

## 故障诊断报告

主菜单选择“检查与故障报告”，可以继续执行原有的“服务与配置检查”，也可以一键生成只读诊断报告。生成报告不会修改用户、分流、配置或流量数据，也不会重启服务。

如果用户数据中的到期时间损坏，自动到期任务会明确记录告警、跳过这条记录并继续处理其他用户，避免一条坏数据阻断整批检查。“服务与配置检查”会把该用户标记为“需要处理”；脚本不会猜测或自动改写正确日期，请人工确认后通过“调整用户有效期”修正。

报告包含以下信息：

- 管理脚本、sing-box、Nfuse 和 sing-box 当前通道版本。
- 三项服务、sing-box 配置、Nfuse 通信、用户数据及未完成操作状态。
- 用户和分流的数量汇总，不包含名称、端口、流量、密码或客户端配置。
- 服务与配置一致性结论，以及最近 24 小时内每项服务最多 30 条警告。

脚本会自动隐藏用户、分流、出口、上游服务器、规则集地址、密码、令牌、主机名、IP 地址和日志中的域名。报告仍建议先通过菜单“查看报告内容”确认，再交给维护者。

报告默认保存在：

```text
/root/sb-user-manager-diagnostics/
```

目录权限为 `700`，每份报告权限为 `600`。菜单可以列出、查看、删除单份报告，也可以指定保留数量清理旧报告。诊断报告不属于迁移备份，删除报告不会影响用户、分流或服务。

## sing-box 版本管理

主菜单中的“sing-box 版本管理”会从 sing-box 官方 GitHub Release 查询最新正式版和最新测试版，并提供：

- 查看当前版本、最新正式版和最新测试版。
- 下载指定通道的最新版本，并验证官方 SHA-256 digest 和压缩包内版本。
- 使用下载到临时目录的程序检查现有连接配置，以及启用中和已停用分流引用的远程规则集。
- 检查测试版时，会在临时目录模拟测试版重新整理配置，再让最新正式版读取这份临时配置；如果无法读回，即使测试版本身能够启动，也会提示“不满足安全往返要求”。
- 切换到最新测试版、切换回最新正式版，以及更新当前所在通道。
- 分别保存正式版、测试版和切换前版本的二进制副本，并记录当前通道和版本。

切换会短暂重启 sing-box，但不会修改用户、分流、配额、有效期和 Nfuse 流量记录。切换前会创建完整环境备份并写入恢复记录；下载、配置检查、文件替换、服务启动或状态保存失败时自动恢复原版本。服务器断电或 SSH 异常中断后，下次运行管理脚本也会先恢复未完成的切换。

进入测试版前必须通过测试版到正式版的反向配置检查，并输入大写 `TEST`。切回正式版时必须由正式版直接检查当前配置，并输入大写 `SWITCH`。如果测试版产生了正式版不支持的配置写法，脚本会拒绝降级，不会强行覆盖配置。

当服务器位于测试通道时，主菜单“检测更新”不会把 sing-box 静默降回正式版；请使用“sing-box 版本管理 → 更新当前通道”更新测试版。Nfuse 和管理脚本仍由普通更新入口处理。

## 备份与恢复

脚本使用三层保护，作用不同：

- **迁移备份（`.sbm` 文件）**：由你在菜单中创建，用于把用户、分流、预置内容及其关联关系迁移到另一台已经安装好本脚本的服务器。
- **操作前完整备份**：脚本在安装、接管或恢复前自动创建，仅用于操作失败时还原这台服务器，不能用于换服务器。
- **内部操作备份**：添加、删除或修改用户和分流前自动创建，用于断联、断电或操作失败后的即时恢复，不需要手工管理。

### 加密迁移包包含什么

迁移包包含：

- 用户名称、协议、端口和协议凭据。
- 每月流量、流量计费/自用类型、有效期和启停状态。
- SS2022 方法、AnyTLS SNI，以及旧版用户仍需保留的 ShadowTLS 密码与 SNI 等独立参数。
- 分流名称、适用用户、远程规则集、出口协议及出口服务器密码。
- 用户已经使用的流量；自用用户的不限额累计用量也会随迁移包保留。

迁移包不包含：

- 原服务器 IP、固定域名或订阅地址。
- sing-box、Nfuse 程序和系统服务文件。
- 新服务器原有的 sing-box 基础配置、证书及其他手工添加的节点或路由。
- 不属于本脚本管理状态的第三方配置。

因此迁移后用户密码、端口和配额保持不变，但客户端仍需通过外部订阅系统或手动方式改用新服务器地址。

### 一、在源服务器创建迁移备份

1. 以 root 身份直接运行 `sb-user-manager`。
2. 在主菜单选择“数据备份与恢复”。
3. 选择“创建迁移备份（用于更换服务器）”。
4. 输入至少 8 位的迁移密码，再输入一次确认。密码太短或两次不一致时可以直接重新填写；任一密码输入处输入 `0` 可取消并返回。密码不会写入迁移文件，也无法找回。
5. 创建完成后记下屏幕显示的 `.sbm` 文件位置，以及用户、分流和流量记录数量。

迁移备份不会按计划自动创建。每次准备迁移或进行重要用户调整前，都应手动生成一份新备份，并保留最近一次已经验证可解密的副本。

新备份默认保存在：

```text
/root/sb-user-manager-backups/data/
```

4.6.0 起每份备份只有一个文件：

```text
sb-user-data-版本-时间.sbm
```

- `.sbm` 已加密并带有完整性保护，文件被修改或损坏时会被拒绝。
- 传输、导入、保留或删除时只需处理这一个文件。
- 迁移密码不会保存在文件中，也无法找回。

4.6.0 不再识别或恢复旧的 `.enc + .sha256 + .auth` 三文件备份。升级前应在源服务器保留可运行的旧脚本；升级后请立即重新创建 `.sbm` 单文件备份。

### 二、把迁移包传到目标服务器

1. 先在目标服务器完成 sb-user-manager 的全新部署或环境接管。
2. 使用 SFTP、服务器面板或其他安全传输方式，优先把单个 `.sbm` 文件直接上传到 `/root` 顶层。
3. “添加外部备份文件”会自动发现 `/root` 顶层符合命名规则的普通 `.sbm` 文件；不需要手动移动到脚本备份目录或输入完整路径。
4. 传输过程中不要打开、编辑或重新压缩 `.sbm` 文件。

如果文件位于其他 root 可读目录，仍可在导入菜单中选择“手动输入其他路径”。自动发现不会递归扫描 `/root` 子目录，也不会跟随符号链接。传输完成后应及时删除临时目录中的多余副本。

### 三、在目标服务器添加备份文件

1. 运行 `sb-user-manager`，选择“数据备份与恢复”。
2. 选择“添加外部备份文件”。
3. 如果 `/root` 顶层存在迁移包，脚本会按真实修改时间从新到旧列出文件、大小和完整状态，输入数字即可选择；也可以选择“手动输入其他路径”或输入 `0` 返回。
4. 如果没有自动发现候选，直接输入刚上传的 `.sbm` 文件完整路径；输入 `0` 可以取消并返回。
5. 脚本会先检查文件是否完整，再复制到正式备份目录。
6. 如果正式备份目录已有同名文件，脚本会询问是否覆盖；不确定时选择否，并先检查文件来源。
7. 添加完成后选择“查看已有备份”，确认文件显示为完整且已设置密码。

### 四、先检查备份

1. 在“数据备份与恢复”中选择“检查备份（不会修改服务器）”。
2. 选择 `.sbm` 备份并输入密码。
3. 脚本会检查密码、文件完整性和内部数据，全程不会修改服务器。
4. 选择恢复方式。普通迁移建议直接回车使用“合并到这台服务器”；只有明确要让这台服务器完全变成备份中的状态时，才选择“完全恢复成备份内容”。
5. 遇到同名用户或分流时，脚本会并排说明两边的情况；直接回车默认保留这台服务器上的内容。
6. 预览会列出最终新增、替换、删除的用户和分流，并显示用户已用流量的变化。
7. 如果端口或名称与现有配置冲突，脚本会一次列出所有问题；解决前不会修改服务器。

建议每次传输后先运行一次验证与预览，确认来源、创建时间、数量和变更范围符合预期。

如果要定期检查本机保存的全部迁移包，可以选择“批量体检全部备份（只读）”并输入一次密码。脚本会逐份检查结构、密文摘要、密码认证和解密后的数据结构；使用其他密码的备份会单独标记为“密码不匹配或认证失败”，不会被直接判为损坏。批量体检不代替恢复前对目标备份进行的单份预览。

### 五、在目标服务器恢复

1. 在“数据备份与恢复”中选择“从备份恢复”。
2. 脚本会按编号列出已有迁移包；选择需要恢复的备份，输入 `0` 可以返回上一级。
3. 输入创建备份时设置的密码。错误密码、损坏密文或认证不一致都会被拒绝，不会修改目标数据。
4. 选择恢复方式：
   - **合并到这台服务器（推荐）**：保留已有内容，只加入缺少的项目。
   - **完全恢复成备份内容**：删除这台服务器当前由脚本管理的用户和分流，再使用备份内容。
5. 合并时如果遇到冲突，请按屏幕说明选择：
   - “保留这台服务器上的项目”是默认且最安全的选择。
   - “使用备份覆盖”会采用备份中的端口、凭据、配额和用量，原客户端配置可能失效。
   - “作为新项目导入”会要求填写新的用户名和端口，或新的分流名称和出口名称；用户改名后，关联分流和已用流量会自动跟随。
   - 输入 `0` 会取消整次合并，服务器不会发生变化。
6. 脚本显示最终变更摘要和完整预览。合并恢复需输入大写 `MERGE`，完全恢复需输入大写 `RESTORE`；输入其他内容会取消。
7. 确认后，脚本先创建操作前完整备份，再按预览结果建立用户、分流和流量统计。
8. 完成前会自动检查服务和配置；任一步骤失败都会尝试恢复操作前的数据。
9. 无论成功还是自动还原，脚本都会在 `/root/sb-user-manager-backups/reports/` 保存一份恢复记录，其中不包含用户或出口服务器密码。

两种方式都不会删除这台服务器上由其他工具或手工添加的 sing-box 配置。拿不准时始终选择“合并到这台服务器”，遇到冲突直接回车保留本机内容。

### 六、恢复后检查

恢复成功后建议依次检查：

1. 返回系统管理，选择“查看服务状态”，确认 sing-box、Nfuse 和到期检测定时器均为正常状态。
2. 选择“服务与配置检查”，确认显示“一切正常”。
3. 进入“用户管理 → 查看用户”，核对用户数量、协议、端口、状态、配额、有效期和已用流量。
4. 进入“分流管理 → 查看分流”，核对分流名称、适用用户、状态和出口协议。
5. 导出一个用户配置进行客户端连通测试；服务器地址应填写新服务器 IP，或由外部订阅系统下发新地址。
6. 确认迁移无误后，删除目标服务器临时上传目录中的副本；正式备份目录中的加密迁移包可按需保留。

### 查看和删除迁移包

- “查看已有备份”会先显示迁移备份、完整回滚备份、内部操作备份和恢复记录的数量、磁盘占用与保留方式，再列出 `.sbm` 文件名、大小和完整状态；不需要输入密码。
- “查看备份内容”需要密码，会显示创建时间、来源服务器、脚本版本和数据数量，不显示用户或出口服务器密码。
- “删除迁移备份”只删除选中的 `.sbm` 文件，不会删除已经恢复到服务器中的用户和分流。
- 删除前应确认至少还有一份位于其他安全位置且已经验证可解密的备份。删除操作无法撤销。

### 冲突和失败如何处理

- **端口被其他服务监听**：迁移会保留原用户端口，应先释放目标服务器上的冲突端口；确需更换端口时，应在源服务器重新创建对应用户后再生成迁移包。
- **名称与现有配置冲突**：脚本不会覆盖与当前分流无关的其他配置。与当前分流使用同一远程规则集地址的旧路由会由脚本统一整理；其他重名情况请按屏幕提示更换名称。
- **文件完整性检查失败**：`.sbm` 文件可能在传输时损坏或被修改，请重新上传原始文件。
- **密码验证失败**：先确认密码是否正确；如果密码无误，请不要继续使用该副本，重新取得可信的备份文件。
- **恢复中途失败**：脚本会自动还原操作前的数据。完成后请检查“查看服务状态”和“服务与配置检查”；如果提示自动还原失败，请停止继续操作并保留屏幕显示的备份位置。
- **SSH 断开或手动中断**：脚本会立即尝试撤销本次修改，并清理临时文件。
- **断电或强制终止**：重新运行脚本时会先自动恢复上次未完成的操作，恢复成功后才显示主菜单。
- **自动恢复失败**：脚本会保留恢复记录和完整备份，并停止后续修改。不要手工删除提示中的文件；请保存屏幕输出并进行人工检查。
- **忘记密码**：迁移包没有密码找回机制，只能回到源服务器重新创建备份。

### 清理旧备份

“清理旧备份”会分别询问要保留的最近 `.sbm` 迁移备份数量和操作前完整备份数量，默认分别为 10 份和 5 份。

- `.sbm` 迁移备份不会在后台自动删除，只有进入此菜单并确认后才会清理。
- 内部操作备份会在成功操作后自动保留最近 10 组；完整环境快照会在成功创建后自动保留最近 5 份；恢复记录会在成功写入后自动保留最近 20 份。
- 正在用于未完成操作或自动恢复的备份会额外保留，不受数量上限影响。
- 残缺、结构异常、完整性校验失败或符号链接不会被自动删除；快速查看会提示能直接识别的结构问题，真正清理前还会逐份执行完整校验。
- 执行前会显示当前数量、保留数量和待删除数量。
- 必须输入大写 `CLEANUP` 才会永久删除，其他输入均取消操作。
- 保留数量必须位于 1–100，不能使用该功能一次删除全部备份。

### 查看恢复记录

每次恢复完成或失败后，脚本都会生成一份不含密码的记录。进入“数据备份与恢复 → 查看恢复记录”可以：

1. 查看记录列表：显示结果、完成时间、来源服务器、恢复数量和备份名称。
2. 查看记录详情：显示失败步骤、来源版本和操作前完整备份位置等排查信息。
3. 删除一条记录：只删除记录本身，不影响备份文件或已经恢复的数据。
4. 清理旧记录：脚本平时会自动保留最近 20 份有效记录；也可在这里设置保留最近 1–100 份，并输入大写 `CLEANUP` 手动整理。

报告结果会显示为“成功”“失败，已回滚”或“失败，回滚异常”。格式损坏或字段不完整的文件会标记为“报告异常”，脚本不会把它当作有效恢复记录展示详情。报告默认保存在：

```text
/root/sb-user-manager-backups/reports/
```

恢复记录不包含用户密码、协议密钥或出口服务器密码，但仍建议仅允许 root 读取。删除记录不会删除其中提到的操作前完整备份；这些备份仍由“清理旧备份”单独管理。

### 操作前完整备份说明（进阶）

操作前完整备份由脚本自动创建在：

```text
/root/sb-user-manager-backups/时间戳/
```

新版快照包含：

```text
root/                 实际备份文件，保持原目录结构
SNAPSHOT_VERSION      快照格式版本
SYMLINKS.tsv          符号链接清单
MANIFEST.sha256       全部备份文件的 SHA256 清单
```

自动恢复前会先验证版本、符号链接和 SHA256 清单；验证失败时不会停止服务或覆盖现有文件。校验通过后，脚本会先停止到期定时器、sing-box 和 Nfuse，再恢复文件并重新启动服务，以避免覆盖运行中二进制时出现 `Text file busy`。

这种完整备份主要用于脚本自动还原，不建议手工取出其中的单个文件覆盖系统。它包含服务器本地配置和程序，不适合作为跨服务器迁移备份，也不应上传到公开位置。

内部操作备份保存在 `/etc/sing-box/backups/`。它们由脚本按同一次操作产生的完整文件组统一管理，不会被重复装入新的完整环境快照。脚本能识别旧版的“连接配置＋用户状态”备份组和新版增加 Nfuse 数据后的备份组；真正残缺的文件会保留现场，而不是猜测删除。

## 支持环境

- 已完成正式实机验收：Debian 12（x86_64）
- 服务器运行环境只支持 Debian 12；Ubuntu 和其他发行版不在当前支持范围内
- 当前下载的 sing-box 与 Nfuse 资产为 `linux-amd64`，暂不支持 ARM64
- 需要默认 IPv4 路由以及 root 权限；IPv6-only 环境尚未验证

## 已有环境的安装处理

“部署与卸载 → 安装或修复环境”会先判断这台服务器是全新环境、已经完整安装、安装不完整，还是由其他工具安装。检测到其他安装时，可以保留现有 sing-box 配置并加入本脚本管理，也可以在完整备份后重新安装。

保留现有配置时，原来的 sing-box 用户不会自动出现在“用户管理”中，但仍会继续运行。脚本只管理之后通过菜单新建的用户和分流。如果现有流量统计服务使用了特殊存储位置，脚本会停止自动接管，避免破坏原有数据。

## 完整卸载

不再使用本项目时，进入“系统管理 → 部署与卸载 → 完整卸载”。脚本会先显示即将删除和保留的内容，再提供以下选择：

1. 创建新的加密迁移备份后卸载（推荐）。
2. 不创建新备份，直接卸载。
3. 输入 `0` 返回上一级。

卸载会停止所有节点连接，并删除 sing-box、Nfuse、到期检查、用户、分流、配额、流量记录、证书、运行配置、管理脚本、`sbm` 快捷命令及内部回滚材料。用户主动创建或导入的 `.sbm` 加密迁移包会继续保存在备份目录，可在以后重新部署后恢复。

Debian 共用工具不会自动卸载，无法确认属于本项目的 root 文件也不会删除。若当前 SSH 正通过本机 sing-box，脚本会在修改前停止并要求改为直连。卸载过程中如果某一步失败或受到受控中断，会使用临时完整快照恢复原来的文件和服务；只有全部成功后才删除这个临时回滚点。

部署不完整或损坏时应先完成修复再卸载。曾经由本脚本接管的第三方环境不会自动恢复成接管前的样子，完整卸载删除的是当前受管理环境。

## 安全说明

脚本保存的用户资料和 sing-box 配置包含用户及出口服务器密码，应保持 root 专用权限，禁止提交到公开仓库。

从 v4.17.3 起，脚本启动时会自动把旧版完整环境快照的目录权限收紧为仅 root 可访问；无关目录、符号链接和快照内容不会被修改。若自动处理失败，管理菜单仍可使用，并会提示通过“检查与故障报告”确认环境状态。

## 实机验收

仓库中的 `tests/acceptance.sh` 用于在服务器上重复验证管理脚本、sing-box 与 Nfuse 的真实联动。它不是部署所需文件，正式部署仍然只有 `sb-user-manager.sh` 一个脚本。

### 只读验收

默认模式不会修改用户、分流、配置或 Nfuse 数据，适合在现有服务器运行：

```bash
sudo SB_ACCEPTANCE_MANAGER=/usr/local/sbin/sb-user-manager \
  bash tests/acceptance.sh audit
```

它会检查脚本语法和版本记录、`/root` 启动副本、三个 systemd 单元、sing-box 配置、Nfuse Socket 与 JSON 数据、到期定时器、未完成事务日志和管理数据一致性。

### 发布验收

正式更新完成后使用只读 `release` 模式，一次核对普通只读验收、精确 Release 标签、脚本附件与 SHA-256，以及最近一次完整环境快照：

```bash
sudo SB_ACCEPTANCE_MANAGER=/usr/local/sbin/sb-user-manager \
  bash tests/acceptance.sh release
```

验收工具会匿名读取公开 Release 并核对唯一附件 `sb-user-manager.sh`；也可用 `SB_ACCEPTANCE_RELEASE_ASSET` 明确指定附件名。此模式不会更新脚本、修复配置、重启服务或修改用户和分流。

### 用户生命周期验收

写入型验收必须显式设置确认变量，建议只在测试服务器运行，并确保没有其他管理操作同时进行：

```bash
sudo SB_ACCEPTANCE_CONFIRM=YES \
  SB_ACCEPTANCE_MANAGER=/usr/local/sbin/sb-user-manager \
  bash tests/acceptance.sh lifecycle
```

该模式会先创建完整环境快照，再使用 `accss*`、`accat*` 随机测试用户名和 20001–30000 范围内的空闲端口，验证：

- 原生 SS2022 自用用户和 AnyTLS 计量用户创建。
- sing-box 连接配置、状态文件、Nfuse 账户及端口联动；自用用户使用不限额统计且停用、启用后不清零。
- Surge 与 Shadowrocket 配置导出。
- 用户停用、启用、配额耗尽显示、到期停用、延长或提前有效期和流量清零。
- 测试用户删除及清理后的一致性。

默认不创建分流。需要验证分流生命周期时，额外提供一个可用的 HTTPS `.srs` 或 `.json` 地址：

```bash
sudo SB_ACCEPTANCE_CONFIRM=YES \
  SB_ACCEPTANCE_RULESET_URL='https://example.com/rules.srs' \
  bash tests/acceptance.sh lifecycle
```

分流测试使用不可达的本地占位上游，只验证规则集、出站和管理状态的增加、停用、启用与删除，不会把真实流量发送给第三方上游。

### 空机完整迁移验收

`full` 会临时清空并恢复受管数据，因此只允许在初始用户数和分流数都为零的专用测试服务器执行；不满足条件时会在创建测试对象前拒绝继续。为了同时验证分流迁移，必须提供可用的远程规则集：

```bash
sudo SB_ACCEPTANCE_CONFIRM=YES \
  SB_ACCEPTANCE_RULESET_URL='https://example.com/rules.srs' \
  bash tests/acceptance.sh full
```

若需要验证非默认安装位置、root 启动副本或完整环境快照目录，可使用 `SB_ACCEPTANCE_MANAGER`、`SB_ACCEPTANCE_VERSIONS_FILE`、`SB_ACCEPTANCE_LAUNCHER_PATH` 和 `SB_ACCEPTANCE_ENVIRONMENT_BACKUP_BASE` 覆盖；报告目录可通过 `SB_ACCEPTANCE_REPORT_DIR` 覆盖。

该模式在生命周期验收基础上保留测试分流，创建临时 `.sbm` 单文件迁移包，依次验证覆盖恢复和智能合并恢复。智能合并测试会保留目标服务器独有用户、导入缺失用户及其关联分流，并核对 Nfuse 已用流量。迁移包只保存在本次验收的临时目录，结束后删除。

### 报告和失败处理

报告默认保存在：

```text
/root/sb-user-manager-backups/reports/acceptance-模式-时间-进程号.json
```

报告只包含检查名称、结果、失败原因、脚本版本和最终对象数量，不包含用户密码、导出配置、迁移密码或分流上游凭据；为避免报告用于识别服务器，兼容字段 `hostname` 固定写为 `[redacted]`，不会读取系统原始主机名。写入型验收成功时会逐项删除测试分流和用户并复检对象数量与一致性；任何步骤失败或进程被中断时，会直接恢复验收前环境快照，并复检 sing-box、Nfuse、三项服务和管理数据一致性，在报告中注明恢复结果。

## 开发与回归测试

修改脚本后应在仓库根目录运行：

```bash
bash tools/build-manager.sh --check
bash tests/test-build.sh
bash tests/test-static.sh
bash tests/test-unit.sh
bash tests/test-acceptance.sh
```

开发时修改 `src/` 内的模块，再运行 `bash tools/build-manager.sh` 生成最终的 `sb-user-manager.sh`。部署和 Release 仍然只有这一个脚本；macOS 只可用于本地构建与静态检查，服务器运行只支持 Debian 12 x86_64。

`tests/test-unit.sh` 会隔离验证全新部署、修复、覆盖、外部接管和更新失败等安装决策流程，并启动真实伪终端菜单测试，连续检查菜单提示、用户编号停启用返回路径、终端输入回显、标准输入/输出/错误、工作目录、`umask`、`IFS`、错误陷阱和管理锁文件描述符。`tests/test-acceptance.sh` 使用完全隔离的夹具验证只读验收和脱敏报告，不读取或修改服务器配置。测试需要 `python3`。

`tests/test-static.sh` 还会检查生成脚本中的裸命令目标：目标必须是脚本已定义函数、Bash 内建/关键字，或来自 Debian 基础环境、安装依赖与项目运行时二进制的明确白名单。增加新的外部命令时，必须同时确认安装来源并更新这项门禁，避免未定义函数在少见启动分支中漏到运行期。
