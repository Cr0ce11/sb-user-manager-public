# 部署、验收与回退

## 适用范围

本文说明正式 Release 在 Debian 12 x86_64 测试或正式环境中的标准部署流程。服务器地址、密码、SSH 私钥、Token、用户配置和迁移包密码不得写入本文、Issue、Pull Request 或验收报告。

本文是安装、更新、验收操作和故障回退步骤的主要正式来源。发布门禁、发布授权和发布后检查以 [`RELEASE.md`](RELEASE.md) 为准；项目当前阶段和后续目标分别以 [`../PROJECT.md`](../PROJECT.md) 和 [`../ROADMAP.md`](../ROADMAP.md) 为准。

## 基本原则

- 只从 GitHub Release 获取待部署脚本，服务器上的旧副本不能反向成为代码来源。
- 部署固定版本，不直接执行分支、PR 附件或来源不明的远程脚本。
- 公开版脚本及其 SHA-256 文件必须来自同一 Release。
- 修改前先确认备份和回退路径；正式环境必须取得项目所有者明确授权。
- 测试服务器和正式服务器分离。破坏性验收只允许在满足保护条件的专用测试环境执行。

## 环境记录

项目记录中只保存以下非敏感信息：

- 环境用途，例如“Debian 12 x86_64 专用测试服务器”。
- 已部署管理脚本、sing-box 和 Nfuse 版本。
- 部署或验收时间、提交、Release、模式和结果。
- 失败后是否自动恢复以及最终一致性状态。

实际地址、端口、账户和凭据应保存在项目所有者控制的密码管理工具中，不提交到 GitHub。

## 部署前检查

1. 确认目标是测试环境还是正式环境。
2. 确认目标 Release、脚本版本和 CHANGELOG 一致。
3. 验证公开版脚本的 SHA-256。
4. 记录当前已安装版本和三项服务状态。
5. 通过脚本创建最新迁移备份，并把加密 `.sbm` 副本保存到服务器外。
6. 确认最近一次操作前完整备份可用；涉及迁移时确认迁移包能够解密检查。
7. 确认回退版本和恢复负责人。

任一检查无法完成时，不进入正式部署。

## 全新安装

1. 将已经校验的公开版脚本放到 root 专用目录，权限设为仅 root 可读写执行。
2. 直接运行脚本，不附加命令。
3. 进入“部署与卸载”，选择“安装或修复环境”，确认脚本识别为全新环境后再开始部署。
4. 安装完成后查看服务状态，确认 sing-box、Nfuse 和到期检测均正常。
5. 执行“服务与配置检查”，必须显示用户、分流、连接配置和流量统计一致。
6. 添加专用测试用户，导出配置并验证真实连通、用量统计和停用行为。
7. 删除测试对象，再次执行一致性检查。

## 版本更新

优先使用脚本菜单“检测更新”，不要手工覆盖 `/usr/local/sbin/sb-user-manager`。

1. 更新前记录当前版本并创建迁移备份。
2. 通过菜单检查当前版本和最新版本。
3. 确认更新后等待脚本切换到新进程。
4. 重新进入主菜单，确认显示目标版本。
5. 查看三项服务状态并执行一致性检查。
6. 在测试服务器运行只读 `release`；涉及用户、流量、分流或服务联动时再运行 `lifecycle`。
7. 核对启动用副本与已安装脚本，避免继续运行旧文件。

## sing-box 服务器怎么办

**sing-box 线已归档。** 「切换到 mihomo 内核」「清理 sing-box 残留」「sing-box 版本管理」三项已整段撤除（[公开 Issue #256](https://github.com/Cr0ce11/sb-user-manager-public/issues/256)），实现连同入口一起删除——留着一段谁都调不到的部署代码，迟早有人以为它还能用。

已经在跑 sing-box 的服务器**不受影响**：用户、分流、流量统计、到期停用与管理脚本自更新都照常。变的是三件事：

- **脚本里没有换内核的入口了。** 要换成 mihomo，只能自己停掉 sing-box、按全新安装装一台 mihomo 机器，再用 `.sbm` 加密迁移备份把用户搬过去。分流需要重建：规则集格式不通用（sing-box 用公网上的 `.srs`／`.json`，mihomo 要本机一个块状 yaml），而**把前者转成后者的工具也一并删掉了**。
- **正式版／测试版通道不再由脚本跟踪。** 「检测更新」仍然**不会**把一台装着测试版的机器静默换成正式版——这条保护留着，判据改成直接看版本号（sing-box 的测试版版本号带 `-`）。要换测试版请自行处理 sing-box 二进制。
- **「验证分流是否生效」在 mihomo 上仍然不可用**（[公开 Issue #187](https://github.com/Cr0ce11/sb-user-manager-public/issues/187)，mihomo 的连接日志不记入口标签）。这一条与本次撤除无关，只是搬到 mihomo 之后会遇到。

真要退回或迁移，依据始终是**服务器外那份 `.sbm` 加密迁移备份**。机器上的「操作前完整环境快照」是给自动回滚用的，菜单里没有手工恢复入口，而且这是明确的决定，不是待补的功能（[ADR 0032](DECISIONS/0032-environment-snapshot-serves-automatic-rollback-only.md)）。

## 完整卸载

完整卸载会停止全部节点并删除受管理环境，只能在已经确认不再提供服务时执行。正式环境卸载属于破坏性操作，必须单独建立任务、保存服务器外迁移包并取得项目所有者明确授权。

1. 先把最新 `.sbm` 加密迁移包保存到服务器外，并确认密码能够完成“检查备份”。
2. 确认当前 SSH 不经过这台服务器自己的 sing-box 节点。
3. 进入“系统管理 → 部署与卸载 → 完整卸载”。
4. 优先选择“创建新的加密迁移备份后卸载”；如果明确不保留当前新增数据，才选择不创建新备份。
5. 核对删除范围后输入 `1` 确认；输入 `0` 返回时服务器不得发生变化。
6. 等待脚本报告完整卸载完成并自行退出，不要在过程中重复连接运行另一个副本。
7. 确认三项服务、systemd 单元、程序、配置、运行数据、管理脚本和 `sbm` 均已移除。
8. 确认用户 `.sbm` 迁移包仍然存在且与服务器外副本摘要一致。

脚本会在删除前创建只服务于本次失败恢复的完整快照，并写入持久化环境事务。任一步骤失败或受到受控中断时，应先让自动恢复结束，再核对原服务和数据；成功后临时快照、内部操作备份、恢复记录和诊断报告会清理。Debian 共用工具不属于项目专属部署，不随卸载删除。

## 验收模式

- `audit`：只读，不修改对象；所有 Release 发布后都应运行。
- `release`：包含 `audit`，并核对正式 Release 脚本与最新完整环境快照；所有正式更新后都应运行。
- `lifecycle`：创建并清理临时用户和分流；用户、流量、分流或服务行为变化时运行。
- `full`：包含迁移覆盖和合并恢复；只允许在初始用户和分流均为零的专用测试服务器运行。

具体命令、保护条件和报告格式参见 README 的“服务器验收”章节。验收报告不得包含密码、Token、服务器地址、服务器主机名、用户配置或上游凭据；兼容字段 `hostname` 固定使用 `[redacted]`。

## 首次正式上线检查单

### 如何使用

这份检查单由技术执行者逐项完成并保存脱敏结果。项目所有者不需要运行命令，只负责确认上线目标、真实客户端是否可用以及最终“继续、停止或回退”的决定。

- `[ ]` 表示尚未确认；`[x]` 表示已经由对应负责人确认。
- 标有“项目所有者”的项目必须由项目所有者本人确认。
- 带有条件的项目如果不适用，必须写明原因并标记“不适用”，不能直接留空。
- 任一“必须停止”条件出现时，不得为了赶进度跳过、改成警告或上线后再补。
- 本检查单完成不等于自动授权上线；每次正式部署仍需独立 Issue 和项目所有者明确批准。

### 2. 部署过程

- [ ] 已记录实际开始时间，确认当前操作对象仍是身份卡中的正式服务器。
- [ ] 部署前再次验证脚本 SHA-256，不使用分支文件、PR 附件、服务器旧副本或来源不明脚本。
- [ ] 脚本位于 root 专用目录，只有 root 可以读取、修改和执行。
- [ ] 直接运行脚本且不附加命令，通过交互菜单选择与身份卡一致的上线方式。
- [ ] 全新安装时，脚本必须识别为全新环境；识别结果不符时立即停止。
- [ ] 数据迁移时，先查看迁移包摘要和恢复方式，确认数量合理后再恢复；默认使用保留目标数据的合并恢复，只有明确需要覆盖时才选择完全恢复。
- [ ] 更新已有环境时，只使用“检测更新”，不手工覆盖 `/usr/local/sbin/sb-user-manager`。
- [ ] 等待安装、恢复或更新事务完整结束；不在下载、校验、服务重启或新进程接管期间重复运行脚本。
- [ ] 每个关键步骤没有出现回滚异常、未完成事务或无法解释的警告。
- [ ] 实际完成时间和最终脚本版本已经记录。

### 3. 部署后技术检查

#### 版本、服务与数据

- [ ] 管理脚本、root 启动副本和版本记录一致，且与目标 Release digest 相符。
- [ ] sing-box、Nfuse 和到期检测均显示“运行中”且已设置为开机启用。
- [ ] sing-box 配置校验通过，Nfuse 通信正常。
- [ ] “服务与配置检查”显示用户、分流、连接配置和流量统计一致。
- [ ] 只读 `audit` 全部通过，失败项为 0。
- [ ] 用户、分流和 Nfuse 账户数量与上线前或迁移包摘要一致。
- [ ] 没有未完成的数据事务或环境恢复事务。

#### 真实业务验证

- [ ] 为本次计划使用的每种协议建立或选择一个专用测试用户，不使用真实客户账户做破坏性测试。
- [ ] 项目所有者在真实客户端完成连接，能够访问预期目标。
- [ ] 技术执行者确认 Nfuse 用量随真实流量增加。
- [ ] 停用测试用户后连接被阻断，重新启用后恢复；测试过程中不改变真实用户数据。
- [ ] 如果本次使用分流，至少一条分流通过“验证分流是否生效”确认命中正确出口。
- [ ] 临时测试对象已经删除，再次运行“服务与配置检查”并通过。
- [ ] **项目所有者确认实际使用体验可以接受。**

### 4. 上线后观察

#### 上线完成时

- [ ] 三项服务正常，没有异常重启。
- [ ] 用户、分流、Nfuse 数量和事务状态正常。
- [ ] 服务器外加密备份、回退快照和原环境仍然保留。

#### 上线后 30 分钟

- [ ] 三项服务持续运行，没有重复失败或异常重启。
- [ ] 真实客户端仍可连接，Nfuse 用量按预期增长。
- [ ] 到期检测定时器正常，必要分流仍命中正确出口。
- [ ] 最近日志没有新的持续性错误；历史警告不被误判为当前故障。

#### 上线后 24 小时

- [ ] 三项服务、数据一致性、事务状态和磁盘空间正常。
- [ ] 用量统计、配额阻断、到期检测和必要分流没有异常。
- [ ] 再次运行只读 `audit`，失败项为 0。
- [ ] 项目所有者确认主要客户端和实际业务持续可用。
- [ ] 只有以上项目全部完成后，才可以单独决定是否下线原环境或清理旧回退材料。

### 5. 必须停止或回退的情况

出现以下任一情况时立即停止继续修改，不追加临时修补：

- 服务器身份、环境用途、目标 Release、版本或 SHA-256 无法确认。
- 服务器外备份、迁移密码、完整快照或回退负责人任一缺失。
- 脚本事务报告回滚异常，或存在未完成事务。
- 管理脚本、启动副本、版本记录或 Release digest 不一致。
- sing-box、Nfuse 或到期检测无法恢复正常。
- 配置校验、Nfuse 通信、服务与配置检查或 `audit` 失败。
- 用户、分流、配额、有效期或用量数据出现无法解释的变化。
- 真实客户端无法连接、用量不增长、停启用行为异常或必要分流走错出口。
- 密码、Token、密钥、客户端配置或其他敏感信息可能已经泄露。
- 必须临时扩大权限、关闭安全检查或手工修改数据才能继续。

### 6. 回退检查单

- [ ] 已停止继续部署、更新、恢复或添加用户，保留现场和脱敏日志。
- [ ] 如果当前事务尚未结束，先让脚本执行自动恢复，不重复运行另一个管理操作。
- [ ] 自动恢复后检查事务状态；失败时不手工拼接 JSON、Nfuse 数据或 sing-box 配置。
- [ ] 事后才发现问题时，退路是服务器外的 `.sbm` 加密迁移备份，不是操作前完整快照——快照只在操作**当次**失败时由脚本自动还原，没有手工恢复入口（[ADR 0032](DECISIONS/0032-environment-snapshot-serves-automatic-rollback-only.md)）。
- [ ] 数据迁移场景保留服务器外可信 `.sbm`，不损坏或覆盖唯一副本。
- [ ] 回退后核对脚本版本、三项服务、配置、Nfuse、用户、分流和对象数量。
- [ ] 回退后运行只读 `audit`，失败项必须为 0。
- [ ] 项目所有者确认原业务恢复可用，并记录最终结论为“已回退”而不是“上线成功”。

### 7. 脱敏上线记录

最终记录只包含：

- 目标 Release、提交和公开版。
- Debian 版本和架构。
- 开始、完成或回退时间。
- 上线方式、验收模式和检查结果。
- 用户、分流、Nfuse 账户的数量，不记录名称。
- 三项服务、配置、一致性、事务和 `audit` 结果。
- 服务器外备份 SHA-256 是否一致，不记录文件内容或密码。
- 最终结论：成功、停止或已回退。
- 已知限制和后续观察事项。

不得记录服务器地址、端口、账号、密码、Token、私钥、主机名、用户名称、客户端配置、上游凭据、完整规则集地址或迁移包密码。

## 旧私有版管理脚本接管

仍在运行旧私有版时，由下载并校验完成的公开目标脚本主动执行永久接管：

```bash
./sb-user-manager.sh --take-over-installed-manager
```

执行前必须确认：

1. 目标脚本来自公开仓库已经通过 CI 的不可变 Release，并已用外部记录的 SHA-256 校验。
2. 目标文件由 root 拥有、不是符号链接，且不能被组或其他用户修改。
3. 目标版本等于或高于当前安装版本；禁止借渠道切换实施降级。
4. 目标脚本支持当前安装脚本的数据 schema；接管命令本身不会提前迁移业务数据。
5. 没有其他安装、恢复或接管任务正在运行，也不存在尚未恢复的环境事务。

接管只替换正式管理脚本、管理版本记录，以及内容仍与旧安装脚本完全一致的可选 root 启动副本。它不会写用户状态、Nfuse 数据库、证书、分流或 sing-box 配置，也不会调用任何服务启停命令。原脚本和版本记录保存在 `/var/lib/sb-user-manager/manager-handoff/`；活动恢复日志只在替换事务期间存在。失败会立即恢复，异常断电则由下次目标脚本启动先行恢复。

接管后运行 `sbm`，确认主界面显示“公开版”，再执行只读 `audit`。项目不再发布私有版；不要删除恢复目录，直到公开目标版本完成日常使用验证。

## 回退方法

发现严重问题时先停止继续修改并保留现场，不手工拼接 JSON、Nfuse 数据或 sing-box 配置。

按优先顺序处理：

1. 如果当前操作尚未完成，让脚本事务恢复到操作前状态。
2. 操作当次失败时，操作前完整快照由脚本自己使用，无需也无法手工调用（[ADR 0032](DECISIONS/0032-environment-snapshot-serves-automatic-rollback-only.md)）。操作已经成功、事后才发现问题时，走服务器外的 `.sbm` 加密迁移备份：重装一台机器再恢复。
4. 涉及管理脚本渠道接管时，优先让活动恢复日志自动恢复；成功接管后的旧脚本位于 `/var/lib/sb-user-manager/manager-handoff/previous.sh`，但只有确认数据 schema 仍兼容时才允许人工回退。
5. 只有在数据状态已经恢复且兼容性明确时，才重新运行上一正式版管理脚本。
6. 恢复后检查三项服务、sing-box 配置、Nfuse 通信和项目一致性，并记录恢复结果。

旧脚本文件本身不是完整的数据回退方案；直接运行旧版本可能无法识别新格式，因此必须先确认格式兼容。
