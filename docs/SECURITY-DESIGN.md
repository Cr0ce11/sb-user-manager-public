# 安全设计

## 信任边界

程序以 root 身份运行，因此以下输入均视为不可信：

- 终端输入。
- 运行配置内容和文件路径。
- 远程规则集。
- GitHub API 和 Release 元数据。
- 下载的压缩包及程序。
- 外部迁移包。
- 现有 sing-box 配置和 Nfuse 数据。
- systemd 日志中显示的网络内容。

## 必须保持的安全属性

- 不执行配置文件中的 shell 内容。
- 不跟随敏感配置或状态文件的符号链接。
- 不把秘密写入命令行、日志、诊断报告或 Git 仓库。
- 所有远程下载使用 HTTPS，并在安装前验证 digest。
- 解压前限定预期资产和文件位置，不能信任归档内任意路径。
- 删除操作必须验证目标属于受管目录，拒绝空路径和宽泛系统路径。
- 修改 sing-box、Nfuse 和状态文件时必须能够整体回滚。
- 迁移包必须在解密前验证完整性，解密明文及时清理。
- 含密码、证书或私钥的入口 apply package 不得依赖 trap 清理具名临时文件：发布前不能存在目录项，发布后的目标只能是完整、已校验且权限为 600 的普通文件；匿名发布能力缺失时必须失败关闭。
- `ssh-keyscan` 只能发现受管落地当前提供的候选公钥，不能建立信任；入口必须在连接前把唯一 Ed25519 候选的 SHA256 指纹与控制器状态中的人工固定值精确比较，并使用 `StrictHostKeyChecking=yes`。任何变化、缺失或歧义都必须在发送 apply package 前失败关闭。
- 首次登记落地时，扫描得到的主机指纹只能展示并由管理员通过独立渠道核对，不能自动保存为信任来源；受限通道探测只能发送空 stdin，并且必须同时收到非零 SSH 状态和 forced agent 的唯一严格 `invalid_input` 回执，不能用有效 apply package 试连接。
- 一次性 root 引导包只能包含公开绑定材料和受信任运行时，必须在远端执行前核对整包及运行时摘要；不确定结果的回退只能在随机 bootstrap ID 与 root-only 收据精确匹配时卸载，不能因 SSH 失败猜测远端状态或接管既有通道。
- 入口只有在远端成功回执的 revision、配置摘要与本次 package 一致，且当前落地记录仍等于发起时快照时，才能推进 `applied_revision`；旧回执、错包回执和并发变更后的回执不能覆盖新期望状态。
- 经 `run_step_or_rollback` 或 `run_managed_step` 调用的函数不得依赖 `set -e`：Bash 会在条件调用上下文中关闭函数体的 `errexit` 语义。函数内下载、校验、解包、安装、移动、删除或写系统文件的每一步都必须用 `|| return`、`|| die` 或明确条件分支传播失败。

## 高风险变更

以下改动必须在 Pull Request 中单独标记，并增加针对性测试：

- `rm -rf`、`mv`、`install`、`tar` 或系统路径写入。
- `curl`、GitHub Release 解析和自更新。
- root 配置解析、权限和符号链接处理。
- 密码、密钥、证书和迁移加密。
- trap、事务、锁和恢复流程。
- systemd 服务启停。

## 供应链方向

SHA-256 只能证明下载内容与 Release 元数据一致，不能阻止发布后用同一版本号替换附件。Release 必须先以草稿形式上传唯一公开脚本及其 SHA-256 文件，核对 GitHub digest 后一次性发布；同版本已经存在时拒绝覆盖或复用。

仓库使用 GitHub 不可变 Release 锁定未来正式版的标签与附件。迁移到公开仓库后重新评估 Artifact Attestations 和 Ruleset；在正式启用前不宣称具备这些保护，也不引入需要自行保管的长期签名私钥。
