# ADR 0030：分流合并优先于逐条排序

## 状态

已接受并执行。关联 [公开 Issue #91](https://github.com/Cr0ce11/sb-user-manager-public/issues/91)。

## 背景

项目有两条彼此冲突的承诺：

1. **合并**：使用相同「预置规则 + 预置出口」的分流，在 sing-box 运行配置中合并为一条路由，使同一份规则集和同一个出口只加载一次。该行为由 CHANGELOG 的 v4.20.0 与 v4.20.1 记录，是有意设计。
2. **顺序**：分流列表中「数字越小越先匹配」，用户可通过「调整分流顺序」改变优先级。

代码审查发现两者在实现上并不相容。`build_split_runtime_plan` 按 `(运行期规则标签, 运行期出口标签)` 归并路由，合并后的路由停留在组内**最靠前那条分流**的位置。因此：

- 移动组内靠后的分流，运行配置一个字节都不会变；
- 界面却提示「分流优先级已调整」，列表也显示新顺序；
- 当两个规则集的域名有重叠时，流量会走到用户没有预期的出口地区，而用户无从察觉。

即：合并是对的，顺序显示是错的，两者叠加导致界面与事实不符。

## 决定

**保留合并，把「顺序」的单位从「单条分流」改为「合并组」。**

1. 相同「预置规则 + 预置出口」的分流继续合并为一条路由，`rule_sets` 与 `outbound_groups` 的去重逻辑不变。sing-box 仍然只加载一份规则集和一个出口。
2. 「数字越小越先匹配」继续成立，但匹配的单位是合并组，而不是列表中的单条分流。
3. 「调整分流顺序」移动整个合并组，并保持组内成员在存储顺序中相邻，使列表顺序与实际匹配顺序一致。移动前会明确告知将连带移动哪些分流，确认提示中也写明数量。
4. 分流列表新增「匹配位置」列，详情新增「匹配位置」与「合并说明」。共用同一位置的分流会显示相同的匹配位置，用户可以直接看出哪些分流在运行时是一条。
5. 分组键取运行期标签，且必须复用 `split_runtime_rule_tag_from_json` 与 `split_runtime_out_tag_from_json`。这两个函数的回退分支使用 SHA-256，无法在 jq 中重写；另写一套判断迟早会与运行配置的实际分组规则脱节。
6. 停用的分流不进入运行配置，因此不参与分组，匹配位置显示为「未生效」。

## 为什么不取消合并

取消合并可以让每条分流各自排序，实现上也更直观，但会让 sing-box 为每条分流各加载一份规则集和一个出口。规则集需要定期远程下载与更新，出口意味着独立连接；在同一套预置被多个用户复用的常见场景下，资源开销随用户数线性增长。项目所有者在权衡后选择保留合并。

## 影响

- 用户可见变化：分流列表多一列「匹配位置」；移动共用预置的分流时会看到连带移动的提示与确认；详情中的「匹配顺序：第 N 条」改为「列表顺序」与「匹配位置」两项，后者才是真正生效的顺序。
- 不改变运行配置的生成结果、状态 schema、迁移包格式，也不改变既有分流的实际匹配行为 —— 本决定修正的是界面与事实不符，而不是匹配行为本身。
- 既有状态文件无需迁移。存量中合并组成员不相邻的情况仍能正确显示（它们会显示相同的匹配位置），并在下一次移动该组时自动变为相邻。

## 回退

改动集中在分流运行时模块、交互提示与相应测试。还原对应 Pull Request 即可，运行配置的生成逻辑与状态格式均未改变。
