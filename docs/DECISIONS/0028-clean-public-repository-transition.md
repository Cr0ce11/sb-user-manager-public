# ADR 0028：以干净快照建立受保护的公开仓库

## 状态

已批准执行。受保护公开仓库已由干净快照建立并通过公开 PR 与 `main` CI；项目所有者随后决定长期保留原私有仓库及双版本发布，两个仓库不再改名。

## 背景

当前仓库是 GitHub Free 个人账户下的私有仓库。私有仓库的标准托管 Actions 每月只有固定免费分钟数，额度耗尽后，合并到 `main` 的任务会在启动前被 GitHub 阻止。审计与迁移门禁由 [Issue #250](https://github.com/DTB201/sb-user-manager/issues/250) 记录；MIT 许可的单一公开源码快照由 [Issue #252](https://github.com/DTB201/sb-user-manager/issues/252) 记录。

项目已经维护“私有版”和“分享版”：私有版通过只读 GitHub Token 访问管理仓库，分享版剥离管理脚本更新路径。当前仓库还保存 v5 休眠代码、设计文档、历史 Issue、Pull Request 和 Actions 日志。直接把现有仓库改为公开，会一次性公开全部可达历史与协作记录，并允许任何人永久保留 Fork 或副本。

## 决定

不直接修改当前仓库的可见性。公开迁移采用以下边界：

1. 当前仓库保持私有和原名，继续保存旧历史、旧 Release、v5 工作，以及私有版、分享版双版本发布。
2. 从经过审计的当前树生成不含私有令牌更新路径的源码快照，以全新 Git 历史建立公开仓库。
3. 公开仓库 `DTB201/sb-user-manager-public` 是公开版源码、完整 CI 和匿名 Release 的正式来源。新版本必须先在这里通过全部门禁，再把同版本业务变更同步提交到私有仓库；禁止两边独立开发同一功能。
4. 公开仓库只允许项目所有者和明确加入的协作者写入；`main` 必须通过 Pull Request、规定 CI 和对话解决门禁，禁止强制推送和删除。
5. 外部 Pull Request 的工作流默认不运行；只有项目所有者审查代码后才能批准，工作流令牌默认只读且不向外部贡献者提供秘密。
6. 当前仓库的 Issue、Pull Request、Actions 日志、分支和旧提交不迁移到公开仓库；需要保留的产品结论以脱敏文档重新记录。
7. 创建公开或私有 Release、改变现有客户端更新来源，必须取得项目所有者明确授权；两个仓库均保留现名，不执行名称切换。
8. 公开源码采用标准 MIT License；公开 Release 只保留一个匿名更新的 `sb-user-manager.sh`，旧配置中的 `GITHUB_TOKEN` 只为升级兼容而接受并立即丢弃。私有 Release 继续保留私有版、分享版及两份 SHA-256。
9. 私有仓库不重复运行公开仓库已经完成的整套耗时 CI；同步前必须核对版本与公共变更，完成本地双版本确定性构建和针对性测试，私有自动化只保留发布所需的轻量检查。

## 原因

- 标准 GitHub 托管运行器在公开仓库中不计费，可以解除私有仓库免费分钟限制。
- 全新历史避免误公开旧协作记录、已经删除的内部内容和大量 v5 开发分支。
- 公开仓库承担免费完整 CI，解决私有 Actions 分钟不足；私有仓库只在公开门禁全绿后接受单向同步，降低双仓库漂移风险。
- 保留私有仓库原名可以维持现有私有客户端更新地址和双版本使用方式，不需要高风险改名窗口。

## 代价

- 旧 Issue、PR、标签和贡献统计不会自动出现在新仓库。
- 每个版本都要记录公开提交与私有同步提交的对应关系，并核对两个仓库版本一致。
- 公开后任何人都可以阅读、克隆和 Fork；写入限制不能阻止源码传播。
- MIT License 允许外部使用、修改和再分发，也意味着项目所有者不能限制他人保存公开源码副本。

## 回退

公开 Release 前可以关闭候选 PR，不影响当前私有仓库、Release 或客户端。公开 Release 后发现问题时保持两个仓库名称不变，通过递增版本修复；私有同步失败则停止该版本的私有发布，不得用未同步代码冒充同一版本。任何阶段都不删除、公开或重写旧私有仓库历史。
